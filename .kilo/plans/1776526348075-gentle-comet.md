# Plan: Study and Analyze Avalokitam Repository Architecture, Core Logic, and Migration Strategy

## Goal
Study the Avalokitam repository in detail to understand its architecture, locate the core poem parsing logic, and determine the best migration strategy for modernizing the old code.

## Current Findings from Codebase Analysis

### Architecture
Avalokitam is a web-based Tamil prosody analyzer using a client-server architecture:
- **Frontend**: Single-page application (SPA) built with Quasar Framework (Vue.js-based). Handles user interface, input processing, and data visualization. Key files: `src/pages/Index.vue`, `src/components/Scansion*.vue`.
- **Backend**: PHP-based server-side logic for prosody analysis. Stateless, no database required. Key directory: `phpbackend/`.
- **Interaction**: Frontend sends processed Tamil text via HTTP POST to backend API (`phpbackend/api.php`). Backend performs analysis and returns XML data, which frontend parses and renders visually using components like `ScansionDisplay.vue`.

Frameworks and Libraries:
- Frontend: Quasar, Vue.js, Axios, Vue-i18n, XML2JS, Leader-line.
- Backend: Pure PHP with custom classes (e.g., SimpleXMLElement).
- Build/Deployment: Quasar CLI, supports PWA, Electron, Cordova. Deploys to Google App Engine.

Flow:
1. User inputs Tamil verse in frontend.
2. Text is processed (punctuation stripped, modifications applied).
3. POST to backend for analysis.
4. Backend transliterates, parses syllables/feet/linkages, identifies metre.
5. Returns XML; frontend renders results.

### Core Poem Parsing Logic
Located primarily in the `phpbackend/` directory:
- **`parsetreeclass.php`**: Main class (`ProsodyParseTree`) for metre identification, letter counting, and XML output.
- **`yapparungalaparsetree.php`**: Extends `ProsodyParseTree` for detailed syllable parsing (e.g., nE_rpu, nirYpu types).
- **Key Functions**:
  - `GetLetterCount()`: Analyzes letters (vowels, consonants, matras).
  - `GetTextSyllablePattern()`: Parses metremes (syllables: ner/nirai) and feet (word patterns).
  - Metre checking methods (e.g., `CheckVenpaa()`): Validates against Tamil prosody rules for metre types like வெண்பா.
  - Bond analysis: Calculates linkages (talai) between feet.
- **Algorithm**: Rule-based, uses regex for phonological patterns, hierarchical parse tree (verse → lines → feet → syllables), outputs XML for visualization.

### Migration Strategy Assessment
Current stack: PHP backend + Vue.js/Quasar frontend. Strengths: Mature, easy deployment, large ecosystems. Weaknesses: Synchronous PHP limits concurrency, legacy code risks.

Recommended Modern Stack: Rust WebAssembly client-side logic + TanStack Start frontend.
- **Why?**: Client-side WASM moves parsing to browser for privacy/offline use, reduces server load. Rust ensures high performance/safety. TanStack Start provides full-stack framework with type-safe routing/server functions. Leverages Tantivy (Rust search engine) for efficient metrical pattern matching, with smaller compiled WASM (~1.5MB release) than custom logic. Aligns with 2026 trends (WASM for compute, modern frameworks).
- **Alternatives Considered**: Node.js + React (good but server-side); Pure Rust WASM without framework (less ergonomic).

#### Step-by-Step Migration Plan (3-6 Months)
1. **Preparation (1-2 Weeks)**: Audit codebase, set up new stack (Rust/WASM with Tantivy, TanStack Start), train team.
2. **Logic Migration (4-6 Weeks)**: Port prosody parsing to Rust WASM using Tantivy for pattern search, integrate with JS interop.
3. **Frontend Migration (4-6 Weeks)**: Convert Vue/Quasar to TanStack Start, handle state/routing, integrate WASM module.
4. **Integration & Testing (2-4 Weeks)**: Client-side tests, WASM performance validation, bundle size optimization.
5. **Go-Live & Monitoring**: Static deployment, monitor with tools like Sentry.

**Risks**: WASM complexity, browser compatibility. Mitigate with prototypes, fallbacks. Benefit: Smaller bundles (~1.5MB WASM vs larger JS).
